<div role="main"> <H2>Chip Revision</H2> <p><a href="https://docs.espressif.com/projects/esp-idf/zh_CN/v6.0.1/esp32p4/api-reference/system/chip_revision.html">[中文]</a></p> <section> <H2>Overview</H2> <p>ESP32-P4 may have different revisions. These revisions mainly fix some issues, and sometimes also bring new features to the chip. describes the versioning of these chip revisions, and the APIs to read the versions at runtime.</p> <p>There are some considerations of compatibility among application, ESP-IDF version, and chip revisions:</p> <ul> <li><p>Applications may depend on some fixes/features provided by a chip revision.</p></li> <li><p>When using updated version of hardware, the hardware may be incompatible with earlier versions of ESP-IDF.</p></li> </ul> <p> describes how the application can specify its chip revision requirements, and the way ESP-IDF checks the compatibility. After that, there is troubleshooting information for this mechanism.</p> </section> <section> <H2>Versioning Scheme</H2> <p>A chip's revision number is typically expressed as <code>vX.Y</code>, where:</p> <ul> <li><p><code>X</code> means a <strong>Major</strong> wafer version. If it is changed, it means that the current software version is not compatible with this released chip and the software must be updated to use this chip.</p></li> <li><p><code>Y</code> means a <strong>Minor</strong> wafer version. If it is changed that means the current software version is compatible with the released chip, and there is no need to update the software.</p></li> </ul> <p>If a newly released chip does not contain breaking changes, the chip can run the same software as the previous chip. As such, the new chip's revision number will only increment the minor version while keeping the major version the same (e.g., <code>v1.1</code> to <code>v1.2</code>).</p> <p>Conversely, if a newly released chip contains breaking changes, the chip <strong>cannot</strong> run the same software as the previous chip. As such, the new chip's revision number will increment the major version and set the minor version to 0 (e.g., <code>v1.1</code> to <code>v2.0</code>).</p> <p>This versioning scheme was selected to indicate the derivation relationship of chip revisions, and clearly distinguish changes in chips between breaking changes and non-breaking changes.</p> <p>ESP-IDF is designed to execute seamlessly on future chip minor revisions with the same logic as the chip's nearest previous minor revision. Thus，users can directly port their compiled binaries to newer MINOR chip revisions without upgrading their ESP-IDF version and re-compile the whole project.</p> <p>When a binary is executed on a chip revision of unexpected MAJOR revision, the software is also able to report issues according to the MAJOR revision. The major and minor versioning scheme also allows hardware changes to be branchable.</p> <p>Note</p> <p>The current chip revision scheme using major and minor versions was introduced from ESP-IDF v5.0 onwards. Thus bootloaders built using earlier versions of ESP-IDF will still use the legacy chip revision scheme of wafer versions.</p> <section> <H3>EFuse Bits for Chip Revisions</H3> <p>Chips have several eFuse version fields:</p> <ul> <li><p>Major wafer version (<code>WAFER_VERSION_MAJOR</code> eFuse)</p></li> <li><p>Minor wafer version (<code>WAFER_VERSION_MINOR</code> eFuse)</p></li> <li><p>Ignore maximum wafer revision (<code>DISABLE_WAFER_VERSION_MAJOR</code> eFuse). See on how this is used.</p></li> </ul> <p>Note</p> <p>The previous versioning logic was based on a single eFuse version field (<code>WAFER_VERSION</code>). This approach makes it impossible to mark chips as breaking or non-breaking changes, and the versioning logic becomes linear.</p> </section> <section> <H3>EFuse Bits for eFuse Block Revisions</H3> <p>EFuse block has version fields:</p> <ul> <li><p>Major efuse block version (<code>BLK_VERSION_MAJOR</code> eFuse)</p></li> <li><p>Minor efuse block version (<code>BLK_VERSION_MINOR</code> eFuse)</p></li> <li><p>Ignore maximum efuse block revision (<code>DISABLE_BLK_VERSION_MAJOR</code> eFuse). See on how this is used.</p></li> </ul> </section> <section> <H3>Chip Revision APIs</H3> <p>These APIs helps to get chip revision from eFuses:</p> <ul> <li><p>. It returns revision in the <code>major * 100 + minor</code> format.</p></li> <li><p>. It returns Major revision of wafer.</p></li> <li><p>. It returns Minor revision of wafer.</p></li> </ul> <p>The following Kconfig definitions (in <code>major * 100 + minor</code> format) that can help add the chip revision dependency to the code:</p> <ul> <li><p><code>CONFIG_ESP32P4_REV_MIN_FULL</code></p></li> <li><p><code>CONFIG_ESP_REV_MIN_FULL</code></p></li> <li><p><code>CONFIG_ESP32P4_REV_MAX_FULL</code></p></li> <li><p><code>CONFIG_ESP_REV_MAX_FULL</code></p></li> </ul> </section> <section> <H3>EFuse Block Revision APIs</H3> <p>These APIs helps to get eFuse block revision from eFuses:</p> <ul> <li><p>. It returns revision in the <code>major * 100 + minor</code> format.</p></li> <li><p><code>efuse_ll_get_blk_version_major()</code>. It returns Major revision of eFuse block.</p></li> <li><p><code>efuse_ll_get_blk_version_minor()</code>. It returns Minor revision of eFuse block.</p></li> </ul> <p>The following Kconfig definitions (in <code>major * 100 + minor</code> format) that can help add the eFuse block revision dependency to the code:</p> <ul> <li><p><code>CONFIG_ESP_EFUSE_BLOCK_REV_MIN_FULL</code></p></li> <li><p><code>CONFIG_ESP_EFUSE_BLOCK_REV_MAX_FULL</code></p></li> </ul> </section> </section> <H2>Compatibility Checks of ESP-IDF</H2> <p>When building an application that needs to support multiple revisions of a particular chip, the minimum and maximum chip revision numbers supported by the build are specified via Kconfig.</p> <p>The minimum chip revision can be configured via the <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/kconfig-reference.html#config-esp32p4-rev-min">CONFIG_ESP32P4_REV_MIN</a> option. Specifying the minimum chip revision will limit the software to only run on a chip revisions that are high enough to support some features or bugfixes.</p> <p>The maximum chip revision cannot be configured and is automatically determined by the current ESP-IDF version being used. ESP-IDF will refuse to boot any chip revision exceeding the maximum chip revision. Given that it is impossible for a particular ESP-IDF version to foresee all future chip revisions, the maximum chip revision is usually set to <code>maximum supported MAJOR version + 99</code>. The "Ignore Maximum Revision" eFuse can be set to bypass the maximum revision limitation. However, the software is not guaranteed to work if the maximum revision is ignored.</p> <p>The eFuse block revision is similar to the chip revision, but it mainly affects the coefficients that are specified in the eFuse (e.g. ADC calibration coefficients).</p> <p>Below is the information about troubleshooting when the chip revision fails the compatibility check. Then there are technical details of the checking and software behavior on earlier version of ESP-IDF.</p> <section> <H3>Troubleshooting</H3> <ol> <li><p>If the second stage bootloader is run on a chip revision smaller than minimum revision specified in the image (i.e., the application), a reboot occurs. The following message will be printed:</p></li> </ol> <div><pre><code>Image requires chip rev &gt;= v3.0, but chip is v1.0</code></pre> </div> <p>To resolve this issue,</p> <ul> <li><p>Use a chip with the required minimum revision or higher.</p></li> <li><p>Lower the <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/kconfig-reference.html#config-esp32p4-rev-min">CONFIG_ESP32P4_REV_MIN</a> value and rebuild the image so that it is compatible with the chip revision being used.</p></li> </ul> <ol> <li><p>If application does not match minimum and maximum chip revisions, a reboot occurs. The following message will be printed:</p></li> </ol> <div><pre><code>Image requires chip rev &lt;= v2.99, but chip is v3.0</code></pre> </div> <p>To resolve this issue, update ESP-IDF to a newer version that supports the chip's revision (<code>CONFIG_ESP32P4_REV_MAX_FULL</code>). Alternatively, set the <code>Ignore maximal revision</code> bit in eFuse or use a chip revision that is compatible with the current version of ESP-IDF.</p> </section> <section> <H3>Representing Revision Requirements of a Binary Image</H3> <p>For the chip revision, the second stage bootloader and the application binary images contain the <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/system/app_image_format.html#_CPPv418esp_image_header_t" title="esp_image_header_t"><code>esp_image_header_t</code></a> header, which stores information specifying the chip revisions that the image is permitted to run on. This header has 3 fields related to the chip revisions:</p> <ul> <li><p><code>min_chip_rev</code> - Minimum chip MAJOR revision required by image (but for ESP32-C3 it is MINOR revision). Its value is determined by <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/kconfig-reference.html#config-esp32p4-rev-min">CONFIG_ESP32P4_REV_MIN</a>.</p></li> <li><p><code>min_chip_rev_full</code> - Minimum chip MINOR revision required by image in format: <code>major * 100 + minor</code>. Its value is determined by <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/kconfig-reference.html#config-esp32p4-rev-min">CONFIG_ESP32P4_REV_MIN</a>.</p></li> <li><p><code>max_chip_rev_full</code> - Maximum chip revision required by image in format: <code>major * 100 + minor</code>. Its value is determined by <code>CONFIG_ESP32P4_REV_MAX_FULL</code>. It can not be changed by user. Only Espressif can change it when a new version will be supported in ESP-IDF.</p></li> </ul> <p>For the eFuse revision, the requirements are stored in <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/system/misc_system_api.html#_CPPv414esp_app_desc_t" title="esp_app_desc_t"><code>esp_app_desc_t</code></a>, which is contained in the application binary image. We only check the application image because the eFuse block revision mostly affects the ADC calibration, which does not really matter in the bootloader. There are 2 fields related to eFuse block revisions:</p> <ul> <li><p><code>min_efuse_blk_rev_full</code> - Minimum eFuse block MINOR revision required by image in format: <code>major * 100 + minor</code>. Its value is determined by <code>CONFIG_ESP_EFUSE_BLOCK_REV_MIN_FULL</code>.</p></li> <li><p><code>max_efuse_blk_rev_full</code> - Maximum eFuse block MINOR revision required by image in format: <code>major * 100 + minor</code>. Its value is determined by <code>CONFIG_ESP_EFUSE_BLOCK_REV_MAX_FULL</code>. It reflects whether the current IDF version supports this efuse block format or not, and should not be changed by the user.</p></li> </ul> </section> <section> <H3>Maximum And Minimum Revision Restrictions</H3> <p>The order for checking the minimum and maximum revisions during application boot up is as follows:</p> <ol> <li><p>The first stage (ROM) bootloader does not check minimum and maximum revision fields from <a href="https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/system/app_image_format.html#_CPPv418esp_image_header_t" title="esp_image_header_t"><code>esp_image_header_t</code></a> before running the 2nd stage bootloader.</p></li> <li><p>The initialization phase of the second stage bootloader checks that the second stage bootloader itself can be launched on the chip of this revision. It extracts the minimum revision from the header of the bootloader image and checks against the chip revision from eFuses. If the chip revision is less than the minimum revision, the bootloader refuses to boot up and aborts. The maximum revision is not checked at this phase.</p></li> <li><p>Then the second stage bootloader checks the revision requirements of the application. It extracts the minimum and maximum revisions of the chip from the application image header, and the eFuse block from the segment header. Then the bootloader checks these versions against the chip and eFuse block revision from eFuses. If the these revisions are less than their minimum revision or higher than the maximum revision, the bootloader refuses to boot up and aborts. However, if the ignore maximum revision bit is set, the maximum revision constraint can be ignored. The ignore bits are set by the customer themselves when there is confirmation that the software is able to work with this chip revision or eFuse block revision.</p></li> <li><p>Furthermore, at the OTA update stage, the running application checks if the new software matches the chip revision and eFuse block revision. It extracts the minimum and maximum chip revisions from the header of the new application image and the eFuse block constraints from the application description to check against the these revisions from eFuses. It checks for revisions matching in the same way that the bootloader does, so that the chip and eFuse block revisions are between their min and max revisions (logic of ignoring max revision also applies).</p></li> </ol> </section> <H3>Backward Compatibility with Bootloaders Built by Older ESP-IDF Versions</H3> <p>Please check the chip version using <code>esptool chip-id</code> command.</p>

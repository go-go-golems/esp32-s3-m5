Hold during power-on to enter UART download mode. <strong>GPIO0 is a strapping pin and is not available as an application GPIO</strong> (it's not broken out anyway).</li> <li><strong>RESET button</strong> — pulls CHIP_PU low. Standalone reset.</li> <li><strong>MIC</strong> — board's electret, routed through the ES8311 codec.</li> <li><strong>DISPLAY FFC (J2, 22-pin)</strong> — MIPI-DSI panel connector. Uses dedicated DSI pins on the chip; does not consume GPIOs.</li> <li><strong>CAMERA FFC (J1, 22-pin)</strong> — MIPI-CSI camera connector. Same: dedicated CSI pins, no GPIO cost.</li> <li><strong>H4 (4-pin C6 debug header)</strong> — <code>IO9 / GND / RXD / TXD</code>. Flashes the on-board ESP32-C6 module via an external USB-UART. Not on any P4 GPIO — standalone path.</li> <li><strong>USB (MX1.25 4-pin P1)</strong> — USB 2.0 <strong>HS</strong> OTG. Wired straight to ESP32-P4 chip pins 49/50 (the dedicated USB HS PHY). This is the RTL-SDR data path. <strong>Not GPIO24/25</strong> — that's a separate FS PHY.</li> </ul> <hr> <H2 dir="auto">2. Current add-on peripherals (user-wired)</H2> <H3 dir="auto">ST7789 LCD via SPI2 — TK024F3036 module on TK024F304189-SPI breakout</H3> <p dir="auto"><strong>Status</strong>: Verified working (2026-05-16). PFD renders over SPI2 IO_MUX direct on the left header at 40 MHz; <code>display: TK024F3036 320x240 ready</code> followed by <code>pfd: PFD 30 FPS</code> in the serial log.</p> <p dir="auto">The bare TK024F3036 FPC is <strong>parallel-default</strong> (39-pin). The <code>TK024F304189-SPI</code> breakout (silkscreen "TK024F304189-SPI" on the back edge) hard-straps <code>IM1_2 = 3.3V</code> to force the panel into 4-wire SPI mode, adds an RC reset network on <code>RST</code>, and exposes the SPI signals on a <code>P3</code> 13-pin header (and on two 1×4 PH2.0 sockets, electrically identical to the 13-pin header — pick whichever connector is convenient).</p> <p dir="auto">The <code>P3</code> silkscreen reads, top-to-bottom on the breakout:</p> <div><pre><code>GND  3V3  BL  D/C  CS  SCK  MISO  MOSI    ← LCD signals

   GPIO 31    ← LCD D/C

   GPIO 50    ← LCD BL
   GPIO 49    ← (free)</code></pre></div> <p dir="auto">The four SPI signals occupy four contiguous header pins with <strong>no GND in the middle</strong>, so a 4-pin Dupont housing across GPIO 28–31 is safe to use as long as the housing pin order matches the table above.</p> <blockquote> <p dir="auto"><g-emoji>⚠️</g-emoji> <strong>Why this layout?</strong> ESP32-P4 SPI2's IO_MUX direct pins are <strong>GPIO 28–31</strong> (datasheet v1.1, Table 2-3: <code>SPI2_CS_PAD</code>, <code>SPI2_D_PAD</code>, <code>SPI2_CK_PAD</code>, <code>SPI2_Q_PAD</code> on the F2 alternate of these GPIOs). All four are on the Waveshare left header, so SPI2 can bypass the GPIO matrix and stay valid up to ST7789's 80 MHz ceiling. The earlier assignment (GPIO 33/46/47/48 on the right header) routed through the GPIO matrix instead, and worse, sat across a header GND pad that turned multi-pin Dupont housings into guaranteed shorts. That assignment is deprecated.</p> </blockquote> <blockquote> <p dir="auto"><g-emoji>⚠️</g-emoji> <strong>Right-header GND gotcha (legacy note)</strong>: <code>GPIO46 → GND → GPIO47</code> are three adjacent pins on the right header. A multi-pin Dupont housing planted across this region will short one signal to ground. Verified failure mode: SPI host writes look OK in logs, but the panel shows the unmodulated transflective backlight tint (uniform pale blue) because CS/SCK/MOSI/DC is shorted to GND. The left-header layout above avoids this entirely.</p> </blockquote> <p dir="auto">SPI bus is configured at <code>PK_LCD_SPI_HZ = 40 MHz</code> in <code>firmware/main/display.h</code>. The ST7789 data sheet allows higher clocks in suitable layouts, but any move toward 60-80 MHz should be verified on the actual cable or PCB rather than documented as assumed margin.</p> <H3 dir="auto">BNO085 IMU via I²C0 — GY-BN008X 10-pin breakout</H3> <p dir="auto">Verified hardware: <strong><code>GY-BN008X</code></strong> (silkscreen on board, purple PCB, through-hole 1×10 0.1" header). 10 pins total + one <code>BOOT</code> solder pad on the side that we leave open. The breakout has an on-board 3.3 V LDO and 4.7 kΩ I²C pull-ups, so 3.3 V from the ESP host is fine.</p> <p dir="auto">Shares the on-board I²C0 bus with the ES8311 codec (different addresses; no conflict). But the chip body's X/Y/Z axes are what the quaternion is expressed in. The breakout silkscreen (back side) shows the body frame:</p> <div><pre><code>X →
     ┌───┐
   Z •  │
     │  │
     └──┘
       Y ↓</code></pre></div> <p dir="auto">For the PFD to interpret <code>roll / pitch / yaw</code> in the aerospace NED convention used by <code>firmware/main/imu_task.c:188-209</code> (<code>quat_to_euler</code> comment), the body axes must be glued to the "aircraft" frame:</p> <ul dir="auto"> <li><strong>chip +X → device forward</strong> (toward the nose, where the PFD is pointing)</li> <li><strong>chip +Y → device right</strong> (right wing)</li> <li><strong>chip +Z → device down</strong> (toward the belly when level)</li> </ul> <p dir="auto">If physical packaging forces a different mounting, two software fixes are available — pick whichever fits the build:</p> <ol dir="auto"> <li><strong>Constant rotation in firmware</strong> — multiply the incoming quaternion by a fixed mounting quaternion before <code>quat_to_euler()</code>. Cheap, deterministic, zero runtime calibration.</li> <li><strong>BNO085 internal reorient</strong> — send SH-2 <em>Set Reorientation</em> (command <code>0x02</code> on the control channel). The chip stores the offset and applies it to every subsequent report. Survives a soft reset only; <code>Save DCD</code> is needed to persist across power-on.</li> </ol> <p dir="auto">The current firmware includes a fixed mounting quaternion in <code>firmware/main/imu_task.h</code>. Keep the physical mounting and that constant in agreement; changing one without the other produces misleading roll, pitch, and heading.</p> <H4 dir="auto">Tare / cage button (BTN1, GPIO 26)</H4> <p dir="auto">Driven by <code>button_task.c</code>. See §3.4 below.</p> <H3 dir="auto">Tact buttons</H3> <p dir="auto">Four active-low momentary tact switches, each between the named GPIO and any GND pad. <code>button_task.c</code> enables the internal pull-up on all four, so no external resistors are needed:</p> <div><pre><code>GPIO ────┬──── tact switch ──── GND
         │
         └─ INPUT_PULLUP (enabled by button_task gpio_config)</code></pre></div> <p dir="auto">Pressed → GPIO reads <code>0</code>. Released → reads <code>1</code>. But it only converges while the device is <strong>rotating</strong> (figure-8 / multi-axis motion). If the device sits still, <code>acc</code> stays at 0 forever. When <code>acc</code> finally reaches 2 or 3, the heading is usable for this device's situational-awareness UI. The BNO085 saves Dynamic Calibration Data on its own schedule; a TARE long-press persists only the ESP32-side software tare quaternion to NVS.</p> <p dir="auto">If the heading is wrong even after a reboot, either a stale TARE is saved in NVS or the BNO's persisted DCD is bad. Use <strong>TARE very-long-press</strong> to factory-reset:</p> <div><pre><code>TARE very-long-press 10s
   → fires pk_imu_factory_reset()
   → wipes the persisted software tare (NVS key on ESP32)
   → clears BNO's persisted reorientation matrix + DCD
   → pulses RST and replays SH-2 init
   → fusion engine restarts with no prior calibration in flash

Now do figure-8 motion for ~15 s.
   → watch `imu: rpy = ... (acc=N)` log line
   → acc climbs 0 → 1 → 2 → 3 as mag fusion converges
   → BNO persists DCD into its own internal flash automatically
     as accuracy improves — no user action needed

When acc reaches 2 or 3, hold the device in the desired "zero"
orientation, then:
   TARE short-press           → snapshot this pose as the new zero
   TARE long-press 3s         → save that zero pose to ESP32 NVS
                                (so the next boot wakes up zeroed)</code></pre></div> <p dir="auto"><strong>Why UP / DOWN don't fire single-button long press</strong>: if they did, holding UP alone for 3 s would emit <code>UP_LONG</code>, then a UP+DOWN combo landing 2 s later would arrive <em>after</em> the <code>UP_LONG</code> event — two distinct gestures for what feels like one hold. Suppressing single-key long-press on UP and DOWN resolves this cleanly while leaving TARE / MODE long presses untouched.</p> <p dir="auto"><strong>Why only TARE emits very-long-press (≥10 s)</strong>: factory reset is a destructive action that should require a sustained, unambiguous hold the user clearly meant to make. Putting it on the same button as the much more frequent "live tare" + "persist tare" gestures (TARE short / long) keeps related-by-meaning operations under one finger, with the danger gradient (3 s long = recoverable; 10 s very-long = wipe) matching the press effort. MODE's long-press slot is used for soft power off / deep sleep instead — see <code>docs/superpowers/plans/2026-05-21-power-button.md</code>.</p> <H4 dir="auto">Firmware structure</H4> <ul dir="auto"> <li><code>firmware/main/button_task.c</code> — GPIO polling + per-button FSM (4 states: RELEASED / PRESSING / HELD_SHORT / HELD_LONG) + combo detector pass. Reports <code>(id, event)</code> pairs to the registered callback.</li> <li><code>firmware/main/main.c::on_button_event()</code> — single dispatch point.

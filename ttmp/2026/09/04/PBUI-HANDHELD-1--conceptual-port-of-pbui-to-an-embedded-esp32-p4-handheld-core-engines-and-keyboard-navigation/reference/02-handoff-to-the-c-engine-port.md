# Handoff: porting the pbui engine concepts to C++ on the PicoCalc

Direction change (2026-09-04): the engines will be written in C++ for the device, with pbui's *concepts* rather than a 1:1 port. Decision 1 in the design guide (JS engines in QuickJS) is superseded by this; everything else in the guide (hardware evidence, the concept tour, the keyboard shell design, the line model, the phased plan) stands and applies to a C++ implementation.

## The handoff

pbui is a presentation-based UI library: everything on screen is a typed reference `{ type, value }`, and one compiled declaration decides what each reference can do. The part worth carrying to C++ is small and already React-free, and it lives in `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/`. Read it in this order, because each piece builds on the last: `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/actions/typeGraph.ts` (a closed, acyclic nominal type graph answering only `isSubtype` and shortest `distance`), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/context/selector.ts` (one `matchSelector` that every interpreter uses: type reach, nearest active scope, optional condition, returning provenance rather than a boolean), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/actions/conditions.ts` (a deliberately four-operation condition algebra with named predicates as the only thing that reads product facts), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/actions/availability.ts` (four states, not a boolean: available, unavailable-with-reason, inapplicable, hidden, and why the last two differ), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/actions/resolve.ts` (the resolver: per action id, smallest type distance, then nearest scope, then priority, then ambiguity returned as data, with the header comment as the spec), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/actions/perform.ts` (`evaluateFresh`, re-resolve before performing so a stale menu row is refused rather than run), `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/acceptance/resolve.ts` plus `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/interaction/accept.ts` (typed acceptance through subtyping then exposed relations, and the pure accept state machine with fuzzed invariants), and `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/interaction/activation.ts` (the four-way ladder behind Enter). Together that is about 1,500 lines of TypeScript with 166 tests in the same directories; the tests are the behavioural contract and are worth translating alongside the code. `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/model/types.ts` shows the shape of the compiled declaration those engines run over, and `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/pbui-ecommerce/src/presentation/actions.ts` and `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/pbui-ecommerce/src/presentation/runtime.tsx` are the smallest complete example of a product declaring types, scopes, descriptors, rules and relations. Skip `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/presentation/createPbui.tsx`, `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/chrome/`, `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/src/components/` and `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/pbui-workbench/` entirely: that is the React runtime and pointer shell the device does not want. `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/workbench-core/src/commands.ts`, `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/workbench-core/src/session.ts` and `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/packages/workbench-core/src/queries.ts` are optional reading for the deck model (workspaces as trees of leaves, a session as two pointers, and `canClose`), which you may prefer to reimplement as a flat deck at first.

The keyboard shell you are building on top is specified, not designed from scratch, by the handheld prototype in this ticket's `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/ttmp/2026/09/04/PBUI-HANDHELD-1--conceptual-port-of-pbui-to-an-embedded-esp32-p4-handheld-core-engines-and-keyboard-navigation/sources/`: `/home/manuel/workspaces/2026-09-01/add-plot-editor/pbui/ttmp/2026/09/04/PBUI-HANDHELD-1--conceptual-port-of-pbui-to-an-embedded-esp32-p4-handheld-core-engines-and-keyboard-navigation/sources/pbui-handheld.jsx` is a 1,133-line pure reducer over a line model (`L(segs, pres, bg)`; a row that carries `pres` is an object row and participates in caret, hints, accept lighting and menus), and the interesting functions are `availCmds` (verbs offered when something visible can receive them), `enterAccept`/`acceptCands` (the argument slot with digit picks, typed completion, `$n` tray pronouns, `it`, and a default chain from presentation histories), the `handleKey` mode dispatch (`nav cmd accept hint search menu overview help`, plus the Esc ladder), and `runCmd`. ## What "similar concepts, not 1:1" should still keep

- A closed type world with subtyping as substitutability (no payload coercion).
- One selector shared by actions, help and relations, returning provenance.
- Four-state availability and the precedence ladder with ambiguity as data (registration order never decides).
- Re-resolve before perform; refuse with a reason instead of running a stale row.
- Typed acceptance where a tie is a chooser, never a guess.
- One line model between content and pixels; every shell feature reads object rows, never pixels.
- The doc line is derived from the resolver, never hand-authored per type.
